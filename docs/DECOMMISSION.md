# Завершение работы и восстановление стенда

Этот порядок предназначен для удаления стенда после проверки диплома.
Репозитории, подтверждения CI/CD и скриншоты сохраняются. Облачные ресурсы
удаляются в два этапа: основная инфраструктура, затем bootstrap с бакетом state.

## Резервная копия

На управляющем хосте `it`, из чистого рабочего каталога инфраструктуры:

    python3 scripts/archive-stand.py

Нужны инструменты и доступы действующего стенда, включая Skopeo, Docker,
административный kubeconfig, SSH к workers и sudo. Пути другой копии приложения
и SSH-ключа можно передать через `--application` и `--ssh-key`.

Скрипт:

1. Отключает maintenance timer и оба workflow, дожидается завершения CI,
   останавливает выделенный CD-runner.
2. Создаёт закрытый каталог `~/diplom-backups/final-*`.
3. Сохраняет Git bundles обоих репозиториев, Terraform state и outputs,
   локальные параметры, ключи, inventory, SSH-пару, kubeconfig и Helm values.
4. Скачивает текущий образ из Registry в каталог Skopeo с сохранением digest.
   Проверяет digest, загрузку образа из архива и локальный HTTP-тест приложения.
5. Сохраняет Secret Grafana; останавливает три компонента, пишущие данные
   мониторинга, архивирует их каталоги с UID/GID, ACL и xattrs, возвращает replicas.
6. Формирует план удаления ровно 13 ресурсов основной конфигурации. Сверяет
   типы действий, ID с сохранённым state и каталог Yandex Cloud.
7. Проверяет архивы и SHA256 всех файлов; записывает путь к готовой копии
   в `.secrets/decommission-backup-path`.

**Скрипт не выполняет apply и не удаляет облачные ресурсы.** При ошибке каталог
может быть неполным; сообщение `Verified archive` выдаётся только после проверок.
Автоматизация остаётся отключённой. Мониторинг возвращается к одной реплике;
если восстановить replicas не удалось, скрипт сообщает имена компонентов.

Копия содержит закрытые ключи и пароли: каталог имеет права 0700, файлы — 0600.
Сохранить вторую защищённую копию на независимом носителе. Перед использованием
проверить `sha256sum --check SHA256SUMS` из каталога копии.

## Удаление

Применяется сохранённый `destroy.tfplan` через `scripts/with-cloud-env.sh`.
План и конфигурация должны соответствовать проверенной копии. До применения
снова проверить отключение CI/maintenance и контрольные суммы архива.
Ожидаемый результат: 13 удалённых ресурсов и пустой основной state.
Registry provisioner удаляет все образы; Terraform удаляет Registry, ВМ,
их загрузочные диски, статические IP, группы безопасности и сеть с подсетями.

Bootstrap удаляется **после** основной инфраструктуры. В нём отдельно защищён
бакет: `prevent_destroy = true`, версионирование включено. Для удаления нужна
пользовательская авторизация Yandex Cloud, копия локального bootstrap state,
удаление всех версий объектов и маркеров удаления из конкретного бакета.
Обычного удаления текущих объектов недостаточно.

После успешного удаления основной инфраструктуры:

    python3 -m venv .secrets/storage-tools
    .secrets/storage-tools/bin/python -m pip install -r scripts/storage-tools-requirements.txt
    .secrets/storage-tools/bin/python scripts/retire-bootstrap.py --delete

Скрипт заново проверяет архив, пустой основной state, паузу обслуживания и CI.
Внутри каталога резервной копии создаёт отдельную конфигурацию bootstrap,
проверяет план удаления 13 известных ресурсов и их соответствие архивным ID.
Все версии state и lockfile скачиваются с контрольными суммами; неожиданные
объекты или действующая блокировка останавливают выполнение. После очистки
бакета применяется проверенный план. Авторизация Terraform — пользовательский
IAM-токен из текущего профиля yc; для чтения/очистки объектов используется
существующий S3-ключ. Значения ключей и токенов не выводятся.

Без `--delete` выполняются проверки, резервирование версий и создание плана.
Исходные Terraform-файлы не изменяются. Локальный bootstrap state обновляется
из рабочей копии также при частичной ошибке apply. Каталог операции записан
в `.secrets/bootstrap-retirement-path`: после ошибки использовать его для
диагностики, не восстанавливать старый state поверх частично удалённых ресурсов.

Отключение защиты бакета допускается только в отдельной локальной копии
bootstrap для проверенного плана завершения работы. В основной конфигурации
защита сохраняется. Удалять каталог/облако целиком не требуется: они могут
содержать другие проекты.

## Завершающая проверка

После удаления bootstrap, с пользовательским профилем yc и доступом gh:

    python3 scripts/finish-decommission.py --cleanup-github

Скрипт проверяет завершённое удаление и отключение автоматизации, затем читает
списки ВМ, дисков, снимков, образов ОС, адресов, сетей, подсетей, security groups,
шлюзов, таблиц маршрутизации, Container Registry, бакетов и сервисных аккаунтов
в каталоге из резервной копии. Облачные ресурсы он не удаляет. Непустые списки
требуют проверки принадлежности; ошибка API не считается пустым списком.
Проверка охватывает перечисленные типы ресурсов, а не все сервисы облака.

Флаг `--cleanup-github` удаляет только семь Secrets, описанных в REPRODUCE.md,
Variables `IMAGE_REPOSITORY` и `APP_WORKER_IPS` и offline-регистрацию runner
`diplom-app-deploy-it` с меткой `diplom-deploy`. Имена репозиториев закреплены
в скрипте. Другие настройки не удаляются; оставшиеся имена выводятся для проверки.
Без флага выполняется только просмотр. Повторный запуск допустим.

Отчёт `closure-check-*.json` сохраняется внутри закрытого каталога резервной копии.
Локальные timer и runner остаются отключёнными. Исходники, резервные копии,
общий SSH-ключ и пользовательские сессии yc/gh сохраняются.

Пустой Terraform state сам по себе не подтверждает отсутствие ресурсов,
созданных вне Terraform. Результат проверенного удаления описан в
[checks/decommission.txt](checks/decommission.txt).

## Повторное развёртывание

Основная инструкция — [REPRODUCE.md](REPRODUCE.md). Для восстановления после
полного удаления, включая bootstrap, соблюдать следующий порядок.

1. Проверить SHA256 архива. Получить чистые копии репозиториев из GitHub или
   `git clone infrastructure.bundle` / `git clone application.bundle`.
   Из `local-state-and-config.tar.gz` извлекать нужные параметры сначала
   в отдельный закрытый каталог для просмотра.
2. Настроить пользовательский yc CLI, квоты и SSH. Из tfvars перенести параметры,
   актуализировав cloud/folder, `admin_cidrs`, образ ОС и имя бакета.
   Закреплённые версии инструментов указаны в репозитории.
3. Создать bootstrap с **новым локальным state**, выпустить новые ключи Terraform,
   puller и pusher. После удаления сервисных аккаунтов старые ключи недействительны.
   Не копировать их на рабочие пути `.secrets/*-key.json`.
4. Сверить backend с новым бакетом и создать основную инфраструктуру.
   **Не загружать старый state в новый backend:** он описывает удалённые ресурсы.
   Архивный state нужен для сверки состава и параметров.
5. Сформировать новый inventory, проверить SSH host keys, установить Kubernetes
   и получить новый admin kubeconfig. Старые inventory artifacts и kubeconfig
   относятся к удалённому кластеру. Установить Traefik.
6. До установки мониторинга восстановить `monitoring-worker-1.tar.gz` и
   `monitoring-worker-2.tar.gz` на соответствующие новые workers, в пустой
   `/var/lib/diplom-monitoring`. Извлекать через sudo tar с `--numeric-owner`,
   `--acls`, `--xattrs`, сохраняя владельцев. Не распаковывать поверх работающей базы.
7. Сохранённый `grafana-admin-secret.json` скопировать в
   `.secrets/grafana-admin-secret.json` с правами 0600. `prepare-monitoring.py`
   переносит только нужные поля Secret. Запустить `deploy-monitoring.sh`:
   адреса генерируются из новых Terraform outputs. Проверить Grafana и метрики.
   История Prometheus ограничена настроенным сроком хранения.
8. Авторизовать Skopeo новым ключом pusher. Опубликовать каталог `app-image/`
   через `skopeo copy --all --preserve-digests` из `dir:` в `docker://` нового
   Registry, используя закрытый authfile. Сверить опубликованный digest
   с `app-image.txt`, передать digest в `scripts/restore-app.sh`.
   Альтернатива — заново собрать и проверить приложение из сохранённого Git-коммита.
9. Обновить GitHub Secrets новыми ключами, настроить runner и обслуживание,
   зарегистрировать runner в чистом каталоге (старые `.runner` и `.credentials`
   не использовать), синхронизировать Variables через `sync-app-ci-vars.py`. Проверить rollout,
   HTTP обоих workers, Grafana и Terraform `No changes`. Убрать maintenance pause
   и включить автоматизацию только после настройки доступов и адресов.
10. Проверить новый запуск Terraform CI и релиз приложения; актуализировать
    адреса и результаты в README/SUBMISSION.

Повторное создание выделит новые ID и, как правило, новые публичные IP.
Архив позволяет сохранить исходники, образ и данные, но не резервирует старые
адреса и не заменяет доступ к облаку и внешним источникам зависимостей.
